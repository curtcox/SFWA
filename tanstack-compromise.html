The TanStack Compromise.

Level 1 — The 60-second version

What actually happened.

An attacker opened an innocuous-looking pull request against TanStack/router from a renamed fork. TanStack's CI ran a bundle-size benchmark on the PR — and that workflow used GitHub Actions' pull_request_target trigger, which runs fork-controlled code with base-repo permissions. The attacker used that one window of execution to plant a poisoned dependency cache that the real release workflow would later restore. When TanStack maintainers merged unrelated PRs hours later, the release workflow ran, pulled the poisoned cache, and the attacker's code scraped a live OIDC token straight out of the GitHub runner's memory and used it to publish to npm — bypassing the workflow's actual publish step entirely.

The malware that landed on npm harvests cloud and CI credentials, exfiltrates them over the Session onion-routed messenger network (so no domain can be sinkholed), and tries to self-propagate to every other package the victim maintains.

Not novel — recombined. Every link in the chain was published research. Adnan Khan documented the cache-poisoning class in May 2024. The OIDC memory-extraction technique was used verbatim in the tj-actions/changed-files compromise of March 2025. The attacker did not invent anything; they composed.
Level 2 — The three-link chain

One vulnerability would not have been enough.

Three trust boundaries had to be crossed in sequence. Each was the assumption of the next defense. Click any card to drill in.

01
The "Pwn Request" via pull_request_target
A fork PR triggered a workflow that runs with the base repo's secrets and cache scope, then checks out the fork's code and runs a build with it.
›

TanStack's bundle-size.yml workflow was triggered by pull_request_target instead of pull_request. The difference looks subtle but matters enormously: pull_request_target runs in the context of the base repository, with access to its secrets and write access to its cache, while still checking out the merge ref of the PR — i.e., fork-controlled code.

GitHub's first-time-contributor approval gate does not apply to pull_request_target. So the moment zblgg opened PR #7378, the workflow ran without human approval, and the malicious vite_setup.mjs committed to the fork executed on a base-repo-trusted runner. 

on:
  pull_request_target:       # ← runs with base-repo trust
    paths: ['packages/**', 'benchmarks/**']

jobs:
  benchmark-pr:
    steps:
      - uses: actions/checkout@v6.0.2
        with:
          ref: refs/pull/${{ github.event.pull_request.number }}/merge   # ← fork code
      - uses: TanStack/config/.github/setup@main      # transitively uses actions/cache@v5
      - run: pnpm nx run @benchmarks/bundle-size:build   # ← executes fork-controlled code

The TanStack maintainers knew this trigger was dangerous — the YAML even has a comment splitting "untrusted" benchmark work from a separate "trusted" commenting job. The split was correct in spirit but missed two crucial details, which set up link 2.

See: GitHub Security Lab — Preventing pwn requests.

02
GitHub Actions cache poisoning across the fork↔base boundary
The fork's run wrote a poisoned pnpm store to the exact cache key the release workflow would later restore on main.
›

Two facts about GitHub Actions cache that the TanStack workflow author (and almost everyone else) didn't account for:

  • actions/cache@v5's post-job save is not gated by the workflow's permissions:. Cache writes use an internal runner token, not the GITHUB_TOKEN. Setting permissions: contents: read does not block cache mutation.
  • Cache scope is per-repo, shared across triggers. A pull_request_target run on a PR can write entries that a push-to-main run will later read.

The attacker's payload was specifically engineered to compute the exact key the legitimate release workflow uses: 

// The key release.yml would compute on the next push to main:
Linux-pnpm-store-${hashFiles('**/pnpm-lock.yaml')}

// And the exact key the poisoned write produced:
Linux-pnpm-store-6f9233a50def742c09fde54f56553d6b449a535adf87d4083690539f49ae4da11

When the benchmark job ended, actions/cache@v5 dutifully saved the now-poisoned 1.1 GB pnpm store under that key. Then the attacker force-pushed the PR back to main's HEAD, making the visible PR a zero-file no-op, closed it, and deleted the branch — all within a minute. The PR was gone. The cache poison persisted.

The original research. This class of attack was named and demonstrated by Adnan Khan in "The Monsters in Your Build Cache" (May 2024). It is a known GitHub Actions design issue requiring conscious mitigation — not a TanStack-specific bug. adnanthekhan.com
03
OIDC token extraction from the runner process's memory
The poisoned cache restored attacker binaries onto the release runner; those binaries scraped a publish-capable OIDC token out of /proc/<pid>/mem and pushed to npm directly.
›

TanStack uses npm's OIDC trusted-publisher binding, so release.yml legitimately declares id-token: write. That permission tells the runner: when asked, mint a short-lived OIDC token that npm will accept as proof that "this publish came from TanStack/router release.yml on refs/heads/main."

The runner does this lazily — the token is generated in memory only when something requests it, and then handed to the workflow step that needed it. So a token that has been minted but not yet consumed sits in the Runner.Worker process address space.

When the poisoned pnpm store was restored, attacker-controlled binaries landed on disk inside node_modules. They executed during the build step and:

  • Located Runner.Worker via /proc/*/cmdline
  • Read /proc/<pid>/maps + /proc/<pid>/mem to dump the worker's memory
  • Pattern-matched out the OIDC JWT
  • POSTed directly to registry.npmjs.org, bypassing the workflow's defined "Publish Packages" step (which had been skipped, because tests had broken)
Verbatim reuse. The memory-dump script used here is the same Python script — with the attribution comment intact — from the tj-actions/changed-files compromise of March 2025. The attacker did not write new tradecraft. See StepSecurity's writeup.

From npm's perspective, the publish was indistinguishable from a legitimate one: the OIDC token came from a real run of release.yml on main, signed by GitHub. The provenance binding cannot tell which step within the workflow asked for the token.

Why none of these alone is enough

Each link bridges a trust boundary the next defense assumed was solid. pull_request_target alone is fine for labeling and commenting; cache poisoning alone needs an existing publish vehicle; OIDC extraction alone needs existing code execution on the runner. Only the chain works.

Level 4 — What the malware actually does

The payload, in three jobs.

When a developer or CI environment runs npm install against any affected version, npm resolves a malicious optionalDependencies entry, fetches an orphan payload commit from the fork network, and runs its prepare lifecycle script. That script executes a ~2.3 MB obfuscated router_init.js. It does three things:

① Harvest credentials  [expand]

A modular framework with dedicated provider classes scanning common locations and token patterns:

  • AWS — IMDS at 169.254.169.254/latest/meta-data/iam/security-credentials/, Secrets Manager, AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY from env
  • GCP — metadata server
  • Kubernetes — service-account tokens from /var/run/secrets/kubernetes.io/serviceaccount/
  • HashiCorp Vault — VAULT_TOKEN / VAULT_AUTH_TOKEN, defaults probing http://127.0.0.1:8200
  • GitHub — ghp_*, gho_*, ghs_*, ACTIONS_ID_TOKEN, ~/.git-credentials, gh CLI config
  • npm — npm_* tokens, ~/.npmrc
  • SSH — private keys from ~/.ssh/

② Exfiltrate over Session  [expand]

Stolen data is exfiltrated through the Session messenger network — an onion-routed, end-to-end encrypted protocol built on the Oxen service-node swarm. The payload embeds a full Session client:

  • Bootstrap via pinned-TLS seed nodes: seed1/2/3.getsession.org
  • Fetches snode list via Oxen JSON-RPC get_n_service_nodes
  • Resolves the target swarm for the attacker's Session pubkey
  • Routes encrypted messages through dynamically selected snode IPs — no fixed C2 endpoint
  • Larger blobs uploaded to filev2.getsession.org/file/
Why this matters defensively. Snode routing means no domain or IP block list will catch egress; the only static infrastructure is the seed bootstrap and the file server. Defenders cannot seize the C2.

③ Self-propagate  [expand]

If the install host has npm credentials with publishing rights, the payload enumerates other packages the victim maintains via registry.npmjs.org/-/v1/search?text=maintainer:<user> and republishes them with the same injection — turning every compromised maintainer machine into a new attack vector.

It also writes poisoned IDE and AI-agent configuration into local repositories using the GitHub GraphQL createCommitOnBranch mutation — files like .claude/settings.json, .claude/setup.mjs, and .vscode/tasks.json — so that anyone who clones or pulls those repos inherits the execution hook in their editor.

Level 5 — Wider context

TanStack was 42 of 170+.

The TanStack incident does not stand alone. SafeDep identified over 170 npm packages and 401 compromised versions published in a coordinated burst within a five-hour window on the same day. Other scopes hit included:

  • @mistralai — 3 packages, 9 versions (the official Mistral AI SDK for JS, plus Azure and GCP variants)
  • @uipath — 65 packages (the entire UiPath npm scope)
  • @opensearch-project/opensearch — the official OpenSearch JS client
  • @squawk (22 packages), @tallyui (10), @beproduct, @draftauth, @taskflow-corp, others

The non-TanStack victims show a different delivery shape: their package.json was rewritten to strip legitimate build scripts and add a single preinstall hook that downloads a Bun runtime from GitHub releases and uses it to execute the same obfuscated router_init.js payload. A telltale: the loader in the Mistral packages references the payload as tanstack_runner.js — the attacker forgot to rename the constant from their original TanStack template.

The likely interpretation. One attacker, one payload, two delivery mechanisms. TanStack was hit via the elaborate CI chain documented here. The 130-plus other packages were almost certainly published using credentials harvested by earlier runs of the same payload — credentials that the malware's self-propagation logic exists to find. The TanStack chain was the most technically interesting; the rest was simpler and broader.
Level 6 — Defensive playbook

What to do now.

The chain in Level 2 broke because three weaknesses bridged trust boundaries that each defense alone assumed solid. Below, both sides of the supply-chain — the people who install npm packages and the people who maintain repos that publish them — get a checklist tied directly to those links. Tick the items that apply.

For everyone who runs `npm install`

If you depend on npm packages

Developers, application teams, CI pipelines that pull third-party code.
Right now — this specific incident
  • Grep your lockfiles for the affected versions. The full list is in GHSA-g7cv-rxg3-hmpx plus the SafeDep appendix for the wider campaign.
  • Grep for the manifest fingerprint anywhere in node_modules: the string github:tanstack/router#79ac49ee inside an optionalDependencies block is conclusive.
  • If you installed an affected version on 2026-05-11, treat the install host as compromised. Rotate every credential reachable from it: AWS, GCP, Kubernetes, Vault, GitHub (PAT + SSH + OAuth tokens), npm, plain SSH keys.
  • Search every repo you touched for unauthorised commits adding .claude/settings.json, .claude/setup.mjs, .claude/router_runtime.js, or .vscode/tasks.json. The malware uses GitHub's GraphQL createCommitOnBranch to plant these silently.
  • Audit ~/.npmrc, ~/.git-credentials, and ~/.ssh/ for tokens or keys you didn't put there.
Durable — against this whole class of attack
  • Adopt a publish-cooldown policy. Don't auto-install npm versions less than ~24–72 hours old; that window is where almost every supply-chain attack gets caught. Tools: SafeDep pmg, Socket.dev cooldown, Renovate's minimumReleaseAge.
  • Disable install-time scripts by default. Add ignore-scripts=true to .npmrc and allow-list the rare packages that genuinely need them. This single setting would have neutralised this incident on the consumer side.
  • Run npm install only in an ephemeral sandbox — a container or VM without your cloud admin creds, deploy keys, or signing keys mounted in.
  • Add real-time egress monitoring to dev machines and CI runners. Harden-Runner for GitHub Actions; LittleSnitch / Lulu / nftables-based egress filtering on the desktop.
  • Run a malicious-package scanner before deploy: SafeDep vet, Socket, Snyk. Treat any flagged tarball as evidence to investigate, not noise.
  • Don't disable lockfile integrity verification — npm and pnpm check it by default; some monorepo configs accidentally bypass it.
For repo owners who publish

If you maintain a repo that ships to npm

Library maintainers, OSS authors, anyone whose CI pushes to a registry.
Close link 1 · Pwn Request
  • Audit every workflow for pull_request_target. Run grep -rn "pull_request_target" .github/workflows/. For each match, confirm the workflow does NOT check out PR code and execute it.
  • For benchmarks or preview builds that need PR contents, switch to the workflow_run pattern: do the untrusted build under pull_request (no secrets), upload an artifact, let a separate privileged workflow_run consume that artifact. GitHub Security Lab guidance.
  • Enable Settings → Actions → General → "Require approval for all outside collaborators" (not just first-time contributors). Stops fork PRs from running workflows without a maintainer click.
  • Add if: github.repository_owner == 'YourOrg' guards on any workflow that should only run on the canonical repo, never on forks.
  • Pin every third-party action to a full 40-character SHA, never to a tag or branch. Tags can be silently re-pointed (this was the tj-actions vector).
Close link 2 · Cache poisoning
  • Use distinct cache key prefixes for PR-triggered jobs vs main-triggered jobs. Example: prefix with pr-${{ github.event.pull_request.number }} so a PR cache cannot be restored by a push-to-main run.
  • Audit composite and setup-* actions for transitive actions/cache usage. Many "setup" actions cache silently and inherit your cache permissions.
  • For release workflows, prefer fresh npm ci / pnpm install --frozen-lockfile over restoring cached node_modules. Slower; immune to this class.
Close link 3 · OIDC abuse
  • Grant id-token: write at job level, not workflow level. Limit which jobs can mint a publish-capable token; everything else runs without that permission.
  • Put the publish step behind a GitHub Environment with required reviewers. Every publish becomes a manual click-through. This is the single highest-leverage defense and would have stopped this attack at the gate.
  • Enable npm provenance so consumers can verify each publish came from your specific workflow run, commit, and source. docs.npmjs.com.
  • Enable npm 2FA at the org level — both for login and for publish.
  • Reduce maintainer count on critical scopes. Every maintainer is an additional credential-theft target; TanStack noted seven maintainers meant seven separate blast-radius sources.
Detection — for when prevention fails
  • Run Harden-Runner (or equivalent CI EDR) on every release workflow. It detected the tj-actions compromise via anomalous egress and would detect Session-network exfil the same way.
  • Subscribe to a publish-monitoring feed for your scope (Socket, SafeDep, npm's own audit log) so you get a second signal about your own publishes — independent of the CI pipeline that produced them.
  • Watch your fork network for warning signs: renamed forks of your repo, orphan branches, force-pushes that wipe themselves within minutes, [skip ci] commits from contributors with no history, and PRs that suddenly add a github: entry to optionalDependencies.
The one-line summary, if you read nothing else. Consumer side: ignore-scripts=true in .npmrc plus a 24-hour install cooldown. Maintainer side: gate every npm publish behind a GitHub Environment with required reviewer approval. Those two settings break this whole class of attack on both ends.
